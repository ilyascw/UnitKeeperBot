# UnitKeeper Mini App: текущее состояние функционала и экранов

## Назначение документа

Документ фиксирует, что сейчас реально есть в Telegram Mini App UnitKeeper, какие пользовательские сценарии уже подключены к backend, какие экраны существуют в коде, и какие пробелы нужно учитывать при передаче интерфейса в дизайн.

Актуальный код miniapp находится в `miniapp/src`. Основные источники:
- `miniapp/src/routes/AppRoutes.tsx`
- `miniapp/src/screens/*`
- `miniapp/src/api/*`
- `docs/legacy-functionality.md`
- `miniapp/PLAN.md`

## Контекст продукта

UnitKeeper - сервис для группового учета домашних/командных задач в Telegram.

Базовая логика:
- пользователь открывает Telegram Mini App из бота;
- backend авторизует пользователя через Telegram init data;
- пользователь либо создает группу, либо вступает в существующую;
- внутри группы есть участники, владелец, код вступления, спринт, веса участников и балансы;
- задачи имеют стоимость в юнитах и частоту выполнения за спринт;
- выполненные задачи влияют на прогресс спринта и балансы.

Текущая miniapp пока покрывает только основу: авторизацию, onboarding, создание/вступление в группу, карточку группы, настройки группы, веса участников и выход из группы. Экраны задач, прогресса, баланса и переводов в miniapp еще не реализованы.

## Роли пользователей

### Новый пользователь без группы

Пользователь уже авторизован через Telegram, но у него нет активной группы.

Доступные действия:
- создать новую группу;
- вступить в существующую группу по названию и коду.

### Участник группы

Обычный участник видит:
- название группы;
- баланс группы;
- параметры текущего спринта;
- список участников;
- веса и балансы участников;
- возможность выйти из группы.

Не может менять настройки группы и веса.

### Владелец группы

Владелец видит все, что видит участник, плюс:
- код вступления;
- действия владельца;
- настройку кода вступления;
- настройку старта и длительности спринта;
- редактирование весов участников;
- особый сценарий выхода с передачей владения или удалением группы, если он последний участник.

## Текущая навигация

Приложение использует hash routes внутри Telegram Mini App.

| Route | Экран | Назначение |
| --- | --- | --- |
| `/` | `HomeScreen` | Технический роутер: отправляет пользователя либо в onboarding, либо в группу |
| `/onboarding` | `OnboardingScreen` | Стартовый экран для пользователя без группы |
| `/onboarding/create` | `CreateGroupScreen` | Создание группы |
| `/onboarding/join` | `JoinGroupScreen` | Вступление в группу |
| `/group` | `GroupScreen` | Основной экран текущей группы |
| `/group/settings` | `GroupSettingsScreen` | Настройки группы, только для владельца |
| `/group/weights` | `GroupWeightsScreen` | Редактирование весов участников, только для владельца |
| `*` | `NotFoundScreen` | Ошибка неизвестного маршрута |

## Общий shell и состояния

### App shell

Текущий layout:
- мобильная колонка;
- максимальная ширина `640px`;
- фон берется из Telegram theme variables;
- основные элементы построены на `@telegram-apps/telegram-ui`: `List`, `Section`, `Cell`, `Input`, `Select`, `Button`, `Placeholder`, `Info`.

Дизайн сейчас в основном системный, без собственного визуального языка.

### Авторизация

Miniapp не отправляет user id напрямую. При запуске:
1. клиент берет Telegram init data;
2. отправляет `POST /auth/telegram`;
3. backend проверяет подпись и возвращает session token;
4. token хранится на клиенте;
5. при перезагрузке проверяется через `GET /auth/me`.

Состояния:
- загрузка: `Signing you in...`;
- не из Telegram: экран `Open from Telegram`;
- ошибка входа: `Couldn't sign you in`;
- успешная авторизация: рендерятся маршруты miniapp.

Проблема для дизайна: тексты авторизации сейчас на английском.

## Экран: Home

Файл: `miniapp/src/screens/HomeScreen.tsx`

Назначение:
- техническая развилка после авторизации;
- запрашивает текущую группу через `GET /groups/current`;
- если backend вернул группу, делает redirect на `/group`;
- если пользователь без группы, делает redirect на `/onboarding`.

Видимые состояния:
- загрузка: `Loading your group...`;
- ошибка загрузки: общий error state с кнопкой retry.

Для дизайнера:
- отдельный макет полноценного Home сейчас не нужен;
- нужно предусмотреть понятные loading/error состояния для всей miniapp.

## Экран: Onboarding

Файл: `miniapp/src/screens/OnboardingScreen.tsx`

Назначение:
- первый экран для пользователя без группы;
- предлагает два основных действия: создать группу или вступить.

Текущий UI:
- центрированный `Placeholder`;
- заголовок `Welcome, {name}`;
- описание на английском;
- две кнопки:
  - `Create group`;
  - `Join group`.

Проблемы:
- весь экран на английском;
- нет объяснения, что такое UnitKeeper и зачем нужна группа;
- нет визуальной иерархии между сценариями;
- нет подсказки, откуда взять код вступления;
- экран выглядит как техническая заглушка.

## Экран: Создание группы

Файл: `miniapp/src/screens/CreateGroupScreen.tsx`

Назначение:
- владелец создает новую группу;
- после успешного создания попадает на экран группы.

Backend:
- `POST /groups`

Поля:
- название группы;
- код вступления, минимум 3 символа;
- день начала периода учета;
- длительность периода в днях;
- timezone определяется автоматически из браузера.

Текущие русские тексты:
- `Создание группы`;
- `Название группы`;
- `Код вступления`;
- `Период учета`;
- `День начала`;
- `Длительность в днях`;
- `Создать группу`;
- `Отмена`.

Валидация на клиенте:
- название не пустое;
- код не короче 3 символов;
- длительность больше 0.

Проблемы:
- нет объяснения, что такое "период учета";
- нет ограничения/подсказки для разумной длительности спринта;
- нет явного подтверждения после создания;
- timezone скрыт, но влияет на расчеты;
- форма выглядит как набор технических полей.

## Экран: Вступление в группу

Файл: `miniapp/src/screens/JoinGroupScreen.tsx`

Назначение:
- пользователь вступает в существующую группу по названию и коду.

Backend:
- `POST /groups/join`

Поля:
- название группы;
- код вступления.

Текущий UI:
- `Join a group`;
- `Group name`;
- `Join secret`;
- `Join group`;
- `Cancel`.

Проблемы:
- экран полностью на английском;
- термин `Join secret` непонятен обычному пользователю;
- не объяснено, что название и код нужно получить у владельца группы;
- нет дружелюбного пустого/ошибочного состояния для неверного кода.

## Экран: Группа

Файл: `miniapp/src/screens/GroupScreen.tsx`

Назначение:
- основная поверхность группы;
- показывает сводку группы, спринт, участников, веса, балансы и действия владельца.

Backend:
- `GET /groups/current`;
- `POST /groups/leave`.

Блоки на экране:
- группа:
  - название;
  - баланс группы;
  - код вступления, только для владельца;
  - timezone в footer;
- спринт:
  - день старта;
  - длительность;
  - текущий период;
  - дата/время окончания;
- участники:
  - имя или username;
  - маркер владельца;
  - вес участника;
  - баланс участника;
  - пометка `(you)` для текущего пользователя;
- действия владельца:
  - `Group settings`;
  - `Edit weights`;
- выход из группы:
  - кнопка `Leave group`;
  - подтверждение выхода;
  - предупреждение о передаче владения или удалении группы.

Проблемы:
- большая часть текста на английском;
- слишком много технических данных на одном экране;
- нет главного dashboard: что нужно сделать сегодня, сколько осталось задач, как идет спринт;
- баланс и веса показаны без объяснения;
- дата периода отображается технически;
- owner actions выглядят как системное меню, а не продуктовый сценарий;
- выход из группы занимает отдельный большой блок на основном экране, хотя это редкое действие.

## Экран: Настройки группы

Файл: `miniapp/src/screens/GroupSettingsScreen.tsx`

Назначение:
- владелец меняет код вступления и параметры спринта.

Backend:
- `PATCH /groups/current/settings`

Поля:
- код вступления;
- день старта спринта;
- длительность спринта в днях.

Ограничения:
- доступ только владельцу;
- не-владелец автоматически возвращается на экран группы.

Проблемы:
- экран полностью на английском;
- нет разделения "безопасность/доступ" и "период учета" на уровне смысла;
- нет предупреждения, как изменение периода повлияет на текущий спринт;
- нет явного disabled-состояния, когда пользователь ничего не изменил;
- нет подтверждения успешного сохранения.

## Экран: Веса участников

Файл: `miniapp/src/screens/GroupWeightsScreen.tsx`

Назначение:
- владелец распределяет плановую нагрузку между участниками.

Backend:
- `PUT /groups/current/weights`

Логика:
- у каждого участника есть процент веса;
- сумма всех весов должна быть равна 100%;
- backend также валидирует инварианты.

Текущий UI:
- список input-полей по участникам;
- footer показывает сумму;
- кнопку сохранения нельзя нажать, если сумма не равна 100%.

Проблемы:
- экран на английском;
- понятие веса не объяснено;
- ручной ввод процентов неудобен на мобильном;
- нет быстрых сценариев: "поровну", "скопировать прошлое", "сбросить";
- нет визуального контроля суммы, кроме текста в footer;
- при большом количестве участников экран будет трудно использовать.

## Экран: Not Found

Файл: `miniapp/src/screens/NotFoundScreen.tsx`

Назначение:
- показывается при неизвестном маршруте.

Текущий UI:
- `Screen not found`;
- `This page doesn't exist.`;
- кнопка `Go home`.

Проблемы:
- экран на английском;
- нет объяснения, что можно вернуться в группу или открыть приложение заново из бота.

## Что уже есть в backend, но еще не выведено в miniapp

Эти контракты уже присутствуют на backend-стороне, но текущий frontend их не использует.

### Задачи

Backend endpoints:
- `GET /tasks`;
- `POST /tasks`;
- `POST /tasks/import`;
- `GET /tasks/{task_id}`;
- `PATCH /tasks/{task_id}`;
- `DELETE /tasks/{task_id}`;
- `POST /tasks/{task_id}/increase-frequency`;
- `POST /tasks/{task_id}/decrease-frequency`;
- `POST /tasks/{task_id}/done`;
- `POST /task-logs/{log_id}/approve`;
- `POST /task-logs/{log_id}/reject`.

Нужные miniapp-экраны:
- список задач;
- карточка задачи;
- создание/редактирование задачи;
- импорт задач;
- выполнение задачи;
- очередь подтверждений;
- отклонение с причиной.

### Прогресс спринта

Backend endpoints:
- `GET /sprints/current/results`;
- `POST /sprints/current/close`.

Нужные miniapp-экраны:
- текущий прогресс;
- план/факт;
- выполненные задачи;
- личный вклад;
- история/результаты закрытого спринта.

### Балансы и переводы

По legacy-функционалу нужны:
- просмотр личного баланса;
- перевод юнитов другому участнику;
- история операций;
- объяснение, почему баланс изменился.

В текущей miniapp отдельного экрана баланса нет.

## Главные UX-проблемы текущего состояния

1. Нет единого русского языка интерфейса.
2. Главный экран группы перегружен технической информацией, но не отвечает на ежедневный вопрос пользователя: "что мне сделать сейчас?"
3. Нет dashboard для текущего спринта.
4. Нет визуального объяснения юнитов, весов и балансов.
5. Редкие destructive actions, например выход из группы, занимают слишком заметное место.
6. Владелец и обычный участник видят почти одинаковую структуру, хотя их задачи разные.
7. Нет полноценной навигационной модели для будущих разделов: задачи, прогресс, баланс, настройки.
8. Состояния ошибок и загрузки технические и на английском.
9. Формы выглядят как прямое отражение backend-полей.
10. Нет empty states для задач, балансов, подтверждений и новых групп.

## Рекомендация по продуктовой структуре

Для следующего дизайн-этапа стоит проектировать miniapp не как набор форм, а как ежедневный рабочий интерфейс.

Предлагаемая верхнеуровневая структура:
- `Главная`: текущий спринт, личный план/факт, быстрые действия, pending approvals;
- `Задачи`: список задач, выполнение, создание, редактирование, импорт;
- `Прогресс`: план/факт, breakdown по задачам, результаты спринта;
- `Баланс`: личный баланс, переводы, история;
- `Группа`: участники, настройки, веса, код вступления, выход.

Текущие экраны можно считать MVP-основой, но не финальной информационной архитектурой.
