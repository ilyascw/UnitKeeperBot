# ТЗ для дизайнера: Telegram Mini App UnitKeeper

## Цель работы

Спроектировать понятный, русскоязычный и мобильный интерфейс Telegram Mini App для UnitKeeper.

Текущая miniapp технически работает, но интерфейс собран как MVP на Telegram UI Kit: часть экранов на английском, много backend-терминов, нет главного dashboard, нет нормальной визуальной иерархии. Нужно подготовить дизайн, который можно дальше реализовывать в React + Telegram UI Kit.

## Что такое UnitKeeper

UnitKeeper помогает группе людей распределять и учитывать регулярные задачи.

Пример: семья, соседи, маленькая команда или группа людей договариваются, кто и сколько делает за период. Каждая задача имеет стоимость в юнитах и нужное количество выполнений за спринт. Участники выполняют задачи, подтверждают выполнение друг друга, а система считает прогресс, план/факт и балансы.

## Основные понятия

### Группа

Общее пространство участников. У группы есть:
- название;
- владелец;
- код вступления;
- участники;
- параметры спринта;
- общий баланс.

### Спринт

Период учета задач. Сейчас в backend есть:
- день начала;
- длительность в днях;
- дата начала текущего периода;
- дата окончания текущего периода.

### Задача

Регулярное дело внутри группы:
- название;
- частота за спринт;
- стоимость в юнитах;
- сколько раз уже выполнена;
- сколько осталось.

### Юниты

Внутренняя условная единица полезности/стоимости задачи. Юниты используются для прогресса и балансов.

### Вес участника

Процент плановой нагрузки участника в группе. Сумма весов всех активных участников должна быть 100%.

### Баланс

Личный счет участника в юнитах. Баланс меняется по итогам спринта и при переводах между участниками.

## Пользовательские роли

### Новый пользователь

Задачи:
- понять, что делает приложение;
- создать группу;
- вступить в группу по названию и коду.

### Участник группы

Задачи:
- видеть, что нужно сделать сейчас;
- отмечать задачи выполненными;
- видеть прогресс спринта;
- видеть личный баланс;
- переводить юниты другому участнику;
- выйти из группы.

### Владелец группы

Дополнительные задачи:
- приглашать участников;
- менять код вступления;
- менять параметры спринта;
- распределять веса;
- управлять задачами;
- понимать последствия выхода из группы.

## Платформа и ограничения

Интерфейс работает как Telegram Mini App.

Технические ограничения:
- основной viewport мобильный;
- приложение должно хорошо жить внутри Telegram WebView;
- нужно поддержать светлую и темную тему Telegram;
- желательно использовать паттерны Telegram UI Kit, но не превращать дизайн в голый список системных секций;
- не проектировать desktop-first интерфейс;
- важные действия должны быть удобны одной рукой;
- тексты должны помещаться на узких экранах;
- все пользовательские тексты должны быть на русском.

Текущий стек:
- React;
- TypeScript;
- Vite;
- Telegram UI Kit;
- TanStack Query;
- React Router.

## Что нужно спроектировать

### P0: привести существующий MVP в нормальный вид

Нужно сделать дизайн для уже существующих экранов:
- состояние запуска и авторизации;
- ошибка открытия не из Telegram;
- onboarding без группы;
- создание группы;
- вступление в группу;
- главный экран группы;
- настройки группы;
- редактирование весов участников;
- подтверждение выхода из группы;
- экран ошибки/неизвестного маршрута;
- loading/error/empty states.

Главная задача P0: интерфейс должен быть полностью понятен обычному пользователю на русском языке.

### P1: спроектировать целевую структуру miniapp

Нужно предложить информационную архитектуру для будущих разделов:
- главная;
- задачи;
- прогресс;
- баланс;
- группа/настройки.

Цель: чтобы miniapp стала ежедневным рабочим интерфейсом, а не набором форм.

### P2: будущие продуктовые экраны

Нужно заложить дизайн-паттерны для экранов, которые скоро появятся:
- список задач;
- карточка задачи;
- создание задачи;
- редактирование задачи;
- импорт задач;
- отметка задачи выполненной;
- очередь подтверждений;
- отклонение выполнения с причиной;
- прогресс текущего спринта;
- личный баланс;
- перевод юнитов;
- история баланса.

## Требования к главным экранам

### Onboarding

Нужно:
- объяснить ценность UnitKeeper в 1-2 коротких фразах;
- дать два понятных действия: создать группу и вступить;
- объяснить, что код вступления выдает владелец группы;
- не перегружать пользователя до создания группы.

Нельзя:
- оставлять технические английские тексты;
- использовать термин `secret`;
- показывать backend-термины без объяснения.

### Создание группы

Нужно спроектировать:
- понятную форму создания;
- подсказки для названия и кода вступления;
- объяснение периода учета;
- выбор дня начала;
- ввод длительности;
- состояние ошибки;
- состояние сохранения;
- успешный переход в группу.

Отдельно продумать, как объяснить пользователю, что код вступления надо передать другим участникам.

### Вступление в группу

Нужно:
- форма с названием группы и кодом;
- понятная подсказка, где взять эти данные;
- ошибка неверного названия/кода;
- возврат к onboarding;
- состояние загрузки.

### Главная / экран группы

Текущий экран `/group` перегружен. Нужно предложить более полезную структуру.

На главной пользователь должен сразу понимать:
- какой сейчас спринт;
- сколько осталось до конца;
- что уже сделано;
- что нужно сделать сегодня или в ближайшее время;
- есть ли pending approvals;
- какой у него баланс.

Для группы отдельно показать:
- участники;
- роли;
- веса;
- балансы;
- код вступления для владельца;
- настройки.

Важно разделить ежедневные действия и редкие настройки.

### Настройки группы

Нужно:
- разделить настройки доступа и настройки спринта;
- объяснить последствия изменения периода;
- показать, что доступ есть только владельцу;
- сделать сохранение и отмену понятными;
- предусмотреть ошибку сохранения.

### Веса участников

Нужно:
- объяснить, что вес - это доля плановой нагрузки;
- показать сумму 100% визуально;
- сделать ручное редактирование удобным на телефоне;
- предложить быстрые действия:
  - распределить поровну;
  - сбросить изменения;
  - возможно, сохранить как есть;
- показать ошибку, если сумма не 100%;
- продумать отображение 2, 3, 5 и 10 участников.

### Выход из группы

Нужно:
- убрать выход из группы из слишком заметной позиции на основном экране;
- сделать сценарий намеренным и безопасным;
- объяснить последствия:
  - обычный участник потеряет доступ и сможет вернуться только по коду;
  - владелец передаст владение другому участнику;
  - если владелец последний, группа будет удалена/закрыта.

## Требования к будущим экранам

### Задачи

Нужно спроектировать:
- список активных задач;
- отображение `выполнено / нужно за спринт`;
- стоимость задачи в юнитах;
- быстрый action "выполнено";
- состояние "ожидает подтверждения";
- карточку задачи;
- действия владельца: создать, редактировать, удалить, увеличить/уменьшить частоту.

### Подтверждения

Нужно:
- список задач, ожидающих подтверждения;
- кто выполнил;
- какая задача;
- когда отправлено;
- approve/reject actions;
- reject flow с причиной.

### Прогресс

Нужно:
- план/факт в юнитах;
- процент выполнения;
- разбивка по задачам;
- личный прогресс;
- понятное состояние в начале спринта и после завершения.

### Баланс

Нужно:
- личный баланс крупно и понятно;
- список участников для перевода;
- ввод суммы;
- подтверждение перевода;
- история операций;
- объяснение источников изменений баланса.

## Тональность и тексты

Язык интерфейса: русский.

Тон:
- простой;
- человеческий;
- без канцелярита;
- без backend-терминов;
- без англицизмов, если есть понятный русский аналог.

Примеры замены:
- `Join secret` -> `Код вступления`;
- `Member weights` -> `Нагрузка участников`;
- `Sprint` -> `Период учета` или `Спринт`, если термин объяснен;
- `Group balance` -> `Баланс группы`;
- `Owner actions` -> `Управление группой`;
- `Leave group` -> `Выйти из группы`.

## Состояния, которые нужно отрисовать

Для каждого ключевого экрана нужны состояния:
- loading;
- empty;
- error;
- saving/submitting;
- success;
- validation error;
- permission denied / only owner;
- offline или временно недоступен backend;
- expired session / открыть из Telegram заново.

## Deliverables

Нужно подготовить:
- карту экранов и навигации;
- mobile-first макеты основных экранов;
- dark theme и light theme или понятные правила адаптации под Telegram theme;
- component states для форм, списков, карточек, ошибок и загрузки;
- тексты основных экранов на русском;
- интерактивный prototype ключевых сценариев:
  - новый пользователь создает группу;
  - пользователь вступает в группу;
  - участник смотрит главную и выходит;
  - владелец меняет настройки;
  - владелец редактирует веса;
  - будущий сценарий выполнения задачи;
  - будущий сценарий перевода юнитов.

## Критерии приемки дизайна

Дизайн можно считать готовым, если:
- все текущие экраны покрыты;
- все тексты на русском;
- обычный пользователь понимает, что делать без объяснений разработчика;
- владелец и участник имеют разные, но логичные сценарии;
- ежедневные действия отделены от редких настроек;
- есть состояния ошибок, загрузки и пустых данных;
- дизайн не ломается на узком мобильном экране;
- дизайн учитывает светлую и темную тему Telegram;
- будущие разделы задач, прогресса и баланса вписываются в общую структуру.

## Важные ограничения для дизайнера

- Не менять бизнес-логику без отдельного согласования.
- Не проектировать сценарии, где пользователь вручную вводит Telegram user id.
- Не делать web dashboard вместо Telegram Mini App.
- Не прятать критичные действия вроде подтверждения задачи слишком глубоко.
- Не использовать английские служебные тексты в пользовательском интерфейсе.
- Не делать отдельную маркетинговую главную внутри miniapp: первый экран должен помогать пользователю работать с группой.

## Рекомендуемый порядок работы

1. Уточнить целевую навигацию: табы, нижнее меню или иной Telegram-friendly паттерн.
2. Пересобрать главный экран вокруг ежедневных действий.
3. Перерисовать onboarding и group management.
4. Заложить паттерны для задач, прогресса и баланса.
5. Отдать разработке набор экранов P0, затем расширять до P1/P2.
